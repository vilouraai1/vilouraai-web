# muse-viloura-cf — move vilouraai.com from Vercel to Cloudflare Workers

**Status: DONE, verified locally. Not deployed, DNS untouched.**
Branch: `muse-viloura-cf` (from main `6e30e8c`, the PR #2 redesign).
Repo: `vilouraai1/vilouraai-web`. No PR opened — the parent does the push.

## 0. Summary

vilouraai.com now builds and runs on Cloudflare Workers (free plan)
via the official OpenNext Cloudflare adapter (`@opennextjs/cloudflare`
+ wrangler, Worker name `vilouraai-web`). All 20 pages render, the
forecast section is untouched, both tRPC mutations persist to local
D1, the FormSubmit audit forms are intact, and the /ops loop
(sync + action queue + dashboard page) works end to end against D1.

One deliberate deviation from the brief, documented in §6: the
runtime database access is **raw D1 SQL, not the Prisma Client via
`@prisma/adapter-d1`**. The Prisma adapter path was tried three ways
and cannot work in this stack (evidence below). The Prisma schema
stays as the DDL source of truth; only the runtime client changed.

## 6. Storage decision — D1 (raw SQL), and why not the Prisma adapter

Storage is load-bearing: `Lead` rows (contact form + checklist
dedupe) and the `/ops` loop (`ops_state` dashboard snapshot,
`ops_action` phone commands polled every 30 min by the external
dispatcher). So this is D1, not store-nothing. The task's preferred
path was the Prisma Client via `@prisma/adapter-d1`; it was tried
three ways and each failed on evidence, not on assumption:

1. **`prisma generate --no-engine` + adapter** — the client refuses:
   "Prisma Client was configured to use the `adapter` option but
   `prisma generate` was run with `--no-engine`. Please run `prisma
   generate` without `--no-engine`."
2. **Normal generated client + adapter** — the bundler resolves the
   client to its Node entry (`index.js`), which loads the native
   query-engine binary. In preview: `Prisma Client could not locate
   the Query Engine for runtime "debian-openssl-1.1.x"`. There is no
   native binary in a Worker.
3. **`wasm.js` entry + adapter** — the WASM engine entry resolves
   (via `workerd`/`edge-light` resolve conditions + webpack
   `asyncWebAssembly`), and the build passes, but at runtime the
   engine fails: `no such file or directory, readAll
   '/bundle/static/wasm/d5294e66907a10b1.wasm'`. OpenNext's esbuild
   bundling drops the engine `.wasm` chunk (it is a webpack asset,
   not a module import — `find .open-next -name "*.wasm"` returns
   nothing), and the engine loads that file via node `fs`, which does
   not exist in a deployed Worker. The `prisma-client` generator
   (6.19.3) was also tried and is not engine-free: a clean regenerate
   still emits `libquery_engine-debian-openssl-3.0.x.so.node` and
   imports `@prisma/client/runtime/library`.

Raw D1 SQL has no engine, no WASM, and no bundler risk. The queries
are tiny (one INSERT, one SELECT-dedupe, one upsert, one queue), so
nothing is lost. `src/server/db.ts` owns all SQL; the call sites are
thin wrappers with unchanged response shapes. Tables self-create on
first use (`ensureTables`, same DDL as the migration file, with
`IF NOT EXISTS`). One D1 quirk found and fixed: the binding's
`exec()` rejects multi-line SQL ("incomplete input" at the first
newline), so the DDL in `db.ts` is single-line per statement; the
migration file keeps the readable multi-line form.
